# AMI TSE setup database — byte-level format notes

Source image: `X67ETCC4.43.ROM` (ASRock X670E Taichi Carrara, Aptio V).
Stream analysed: `out/payload/0x1118730_guid-section.bin` (GUID-defined LZMA payload, GUID
`E9D2B238-9537-487F-A29C-490B15FE8D2D`-style compressed region, size 0x10bf80 after
decompression).  Everything below is read out of that decompressed buffer; all offsets are
offsets **inside the decompressed stream**, not inside the ROM.

Parser: `tools/tse/setupdb.py` → `out/settings_map.json`.
Reproduce: `python tools/tse/setupdb.py out/payload/0x1118730_guid-section.bin -o out/settings_map.json --rom X67ETCC4.43.ROM --validate 12`

The main setup UI is generated by AMI TSE from the three structures below. The payload also
contains eight additional independent HII-like formsets (AMD CBS, PBS, RAID and Overclocking);
`setupdb.py` now decodes all nine and marks every entry with its `formset`. The notes in §1–§8
describe the main AMI TSE database specifically. The standard FV/file parsers (`tools/uefi/fv.py`)
see no PE32 in this raw AMI record body, so every database is located by content, not by container.

## 1. Layout of the database

| region | range | content |
|---|---|---|
| auxiliary TSE tables | `0x690000 .. 0x690488` | GUID/token tables (e.g. `5f 15 <AMI GUID> 03 01 00`), not decoded |
| varstore descriptor table | `0x690489 .. 0x690e22` | 68 records, 0x999 bytes |
| form opcode stream | `0x690e22 .. 0x69b044` | 0xa222 bytes, 62 forms / 635 questions |
| string pool | `0x69b044 .. 0x6ea6be` | 9 chained `EFI_HII_PACKAGE_STRINGS` (en-US + 8 others) |

The string `AMITSESetup` at `0x69054b` (the landmark) is the *name field of a varstore
descriptor* (record at `0x690535`), i.e. it sits in the varstore table, not in a string pool.
There is no global header: the table is self-describing through a length byte (§2) and the
opcode stream is self-terminating (§3), the string pool is found by the package signature (§5).

## 2. Varstore descriptor table (`0x690489`)

68 chained records, two tag variants, no count field:

```
tag 0x24 : [u8 tag=0x24][u8 len][u8 guid[16]][u16 varstore_id][u16 size][char name[]]
tag 0x26 : [u8 tag=0x26][u8 len][u16 varstore_id][u8 guid[16]][u32 flags][u16 size][char name[]]
```

* `len` (byte +1) is the **total length of the record including its NUL** — proof: for all 67
  consecutive gaps `data[rec+1] == next_rec - rec` holds, and the last record's length lands
  exactly on the first opcode (`0x690dfb + 0x27 = 0x690e22`).  Reported by the tool as
  `meta.varstore_table = {records: 68, len_byte_matches: 67, len_byte_mismatches: 0,
  start: "0x690489", end: "0x690e22"}`.
* GUIDs are stored in on-disk (little-endian `Data1/Data2/Data3`) order; the JSON prints
  `uuid.UUID(bytes_le=…)`, so the `Setup` store reads `ec87d643-eba4-4bb5-a1e5-3f3e36b20da9`
  while the raw bytes are `43 d6 87 ec a4 eb b5 4b …`.
* 67 records use tag 0x24, one uses 0x26 (`TcgNvmeVar`, `0x6906f1`), which additionally binds to
  the `Setup` GUID and carries a `u32` (= 2).

independent sanity check on the byte framing.

## 3. Form opcode stream (`0x690e22`)

Plain `EFI_IFR_*` opcode sequence (names/numbers from `out/UefiInternalFormRepresentation.h`,
table copy in `tools/tse/ifr_opcodes.txt`): every opcode is `[u8 opcode][u8 length]`,
`length` = total size, `length & 0x7F` used for framing.

Bit 7 of the length byte is **not** a scope flag (AMI usage, measured over the whole stream):

| opcode | bit7=1 | bit7=0 |
|---|---|---|
| `FORM`, `ONE_OF`, `NUMERIC`, `CHECKBOX`, `PASSWORD`, `DATE`, `TIME`, `SUBTITLE`, `SUPPRESS_IF`, `GRAY_OUT_IF`, `DISABLE_IF`, `ACTION` | 62, 323, 297, 9, 4, 1, 1, 226, 520, 190, 1, 3 | 0 |
| `TEXT`, `REF`, `ONE_OF_OPTION`, `DEFAULT`, `END`, `AND`, `OR`, `NOT`, `GUID` | 0 | 200, 118, 1557, 298, 1915, 24, 150, 151, 22 |
| `EQ_ID_VAL` | 260 | 547 |

`EQ_ID_VAL` occurring with both bit-7 values proves the bit cannot open/close a scope
(an expression operand cannot be a scope).  Nesting is therefore *not* reconstructed from bit 7.

Framing proof — `END_OP` (0x29 0x02) count is exactly the number of closeable elements:
`635 questions + 118 REF + 426 TEXT/SUBTITLE + 711 conditions + 3 ACTION + 22 GUID = 1915 = END count`.
So every element carries its own trailing `END`, `ONE_OF_OPTION` / `DEFAULT` / expression
operands do not, and the walk has no drift (a single mis-sized opcode would break the identity).

### Opcode field layouts (offsets relative to the first body byte `b = opcode_ptr + 2`)

```
FORM            0x01  len 0x06  [u16 form_id][u16 title_str_id]
REF             0x0F  len 0x0F  [u16 prompt][u16 help][u16 qid][u16 varstore=0][u16 offset=0xFFFF]
                                [u8 flags][u16 target_form]
              len 0x21  … same + [u16 rsvd][u8 guid[16]]      (cross-formset goto)
ONE_OF          0x05  len 12+3w [u16 prompt][u16 help][u16 qid][u16 varstore_id][u16 var_offset]
NUMERIC         0x07            [u8 flags][u8 width_code]     width_code: 0→1B 1→2B 2→4B 3→8B
CHECKBOX        0x06            [u8 min][u8 max][u8 step]     (NUMERIC/ONE_OF only)
ONE_OF_OPTION   0x09  len 6+w   [u16 text][u16 flags][value w]      flags&0x10 = DEFAULT
                                                                    flags&0x20 = DEFAULT_MFG
DEFAULT         0x5B  len 5+w   [u16 default_id][u8 type][value w]  (type = same width code;
                                                                    measured len: 6/7/9 for w=1/2/4)
PASSWORD        0x08            [u8 min_size][u8 max_size] at b+12/b+13
DATE/TIME       0x1A/0x1B       question header, no varstore value of scalar width
SUPPRESS_IF     0x0A  len 2     ┐ condition wrappers, expression follows, closed by END
GRAY_OUT_IF     0x19  len 2     ├   (EQ_ID_VAL 0x12: [u16 qid][u16 value])
DISABLE_IF      0x1E  len 2     │   (EQ_ID_ID 0x13, EQ_ID_VAL_LIST 0x14: [u16 qid][u16 n][u16…])
END             0x29  len 2     ┘   AND 0x15, OR 0x16, NOT 0x17, TRUE 0x46, UINT8/16/32/64 0x42-0x45
GUID_OP         0x5F  len 0x16  [u8 guid[16]][u16 token]  AMI GUID
                                0F0B1735-87A0-4193-B266-538C38AF48CE, 22 occurrences (H/W Monitor)
```

There is no `varstore`/`offset` inside `REF` in the useful sense (`0x0000`/`0xFFFF`), and the
question → varstore binding is purely `varstore_id` → descriptor table (§2).

## 4. Question → varstore map

`item.offset = var_offset`, `item.size = width_code` (1/2/4/8), `item.varstore` = name from the
descriptor table, `item.qid` = the AMI question id used by the conditions
(`EQ_ID_VAL qid`), so visibility rules are expressed against *other* varstore bytes via the qid
table.  Checks that passed on all 635 items:

* `var_offset + size <= varstore.size` for every item with a known store (0 errors; the whole
  `Setup` store is covered exactly: max offset used = 604 = size).
* 2 numerics have `min > max` read unsigned; re-read as two's complement they become
  `-100 … 500` (`Offset Voltage(mV)`, `Setup+0x15D/0x169`) → flagged `"signed": true`.
* 122 items (all on form `0x2BA9`, the AMI "Exit" container) have `prompt_id = 0`: hidden
  1-byte/2-byte numeric questions bound to offset 0 of stores such as `BootManager`, `Shell`,
  `AMICallback`, `SETUPLAYOUTINFO`, `PlatformLangCodes`.  They decode structurally but have no
  name and no options; they look like AMI's varstore cross-reference list, not real menu items.

## 5. String pool (`0x69b044` … `0x6ea6be`)

```
069b044  28 06 02 04         u32 = length 0x020628 | type 0x04 (EFI_HII_PACKAGE_STRINGS)
069b048  34 00 00 00         u32 header size 0x34
069b04c  34 00 00 00         u32 offset of the first string block (relative to 0x69b044 → 0x69b078)
069b050  … zeros …
069b070  01 00               u16 (fallback/version field, 0x0001)
069b072  65 6e 2d 55 53 00   "en-US", terminated exactly at header_size
069b078  14 45 00 6e 00 67 00 …   EFI_HII_SIBT_STRING_UCS2  → id 1 "English"
```

Block walk (ids start at 1 and increase per string): `0x14 STRING_UCS2`, `0x10 STRING_SCSU`,
`0x16 STRINGS_UCS2` (u16 count), `0x12 STRINGS_SCSU`, `0x20 DUPLICATE` (u16 src id),
`0x21 SKIP2`, `0x22 SKIP1`, `0x30/0x31/0x32 EXT1/2/4`, `0x40 FONT`, `0x00 END`.

Packages are chained back-to-back; the tool follows the chain from the en-US package:

|---|---|---|---|
| en-US | 0x69b044 | 132648 | 2363 |
| zh-cht | 0x6bb66c | 13861 | 384 |
| zh-chs | 0x6bec91 | 14135 | 384 |
| ja-JP | 0x6c23c8 | 17412 | 384 |
| ko-KR | 0x6c67cc | 16840 | 384 |
| fr-FR | 0x6ca994 | 39555 | 510 |

| es-ES | 0x6daf53 | 30372 | 382 |

Only en-US is complete (the others only translate a subset; missing ids fall back to English —
their blocks use `SIBT_DUPLICATE`/`SKIP`).  The JSON contains English text only.

String text contains AMI TSE directives embedded as `ESC '{' <fmt> '#'` and ANSI `ESC [ n;n;m`
(131 + 100 occurrences).  `clean_text()` removes them (`meta.text_cleaning`), e.g.
`\x1b{a1#CAS# Latency (tCL)\x1b{p200#\x1b[1;37;m%d\x1b[;;m` → `CAS# Latency (tCL)`; a trailing
`%d` value placeholder is dropped.  Raw bytes in the pool are untouched.

## 6. Menu hierarchy

Task C: **there is a form → form link**, `EFI_IFR_REF_OP` (`0x0F`), carrying the target form id
(and, for 11 opcodes, the target *formset* GUID).  Paths in `settings_map.json` are a BFS over
those links starting from the form whose title is "Setup" (`0x2710`), so each item has a
`path` / `menu` breadcrumb:

```
Setup(0x2710) → Main 0x2711, Advanced 0x2712, Chipset 0x2713, Security 0x2714, Boot 0x2715, Exit 0x2716
  Advanced → OC Tweaker 0x2b9f, H/W Monitor 0x2ba5 (178 items), Tool 0x2726, CPU Configuration 0x2870,
             Trusted Computing 0x271e/0x271f/0x2720 (3 mutually exclusive variants), USB Configuration,
             NVMe Configuration, CSM, Super IO, "Advanced" 0x2722 (→ PCI Configuration, Storage, …)
  OC Tweaker → DRAM Timing Configuration 0x2b8a, DRAM Bus Control 0x2b8b, DRAM Profile 0x2b8d,
               External Voltage Settings 0x2ba1
58 of 62 forms reachable; unreachable: 0x272b (no title), 0x2938 "HDD Security Configuration",
0x2a5d/0x2a5e "TCG Storage device Security Configuration" — all four are empty containers that
the reference to them keeps behind a GUID_OP/hidden condition.
```

Cross-formset targets (the target's own form/question database is a different TSE/HII module —
`AMD CBS` (`0x7000`, 3 variant GUIDs), `AMD PBS` (`0x000B`), `PCI Configuration`
(`aca9f304-…` = the `PCI_COMMON` store), `IDE Configuration`, `Media Sanitization`) are kept in
`gotos[]` with `cross_formset: true`. AMD CBS/PBS and the other independent databases are decoded
as separate entries in the combined map; their items retain a `formset` label.

Top-level page *ordering* (ASRock's Main/OC Tweaker/Advanced/Tool/Hardware Monitor/Boot/
Security/Exit bar) is not part of the opcode stream — the DB nests ASRock's pages under the
`Advanced` container form (`0x2712`, 31 submenus).  The hints that the setup re-parents pages at
runtime (`SETUPLAYOUTINFO`, `DynamicPageCount` varstores) were found but **not** decoded.

## 7. What is proven vs. inferred

Proven by bytes (each item is checkable in the hexdumps above or by re-running the tool):

1. varstore record framing, incl. the self-describing length byte (67/67 gaps match) and
   `Setup = 604 bytes @ 0x69049b`;
2. question framing: qid/varstore/offset/width at fixed body offsets, cross-checked against
   `Setup`(604), `AMITSESetup`(81), `PlatformLang`(2), `EfiGlobalVariableGuid` assignments;
3. `END` count identity (1915) ⇒ no framing drift in the 0xa222-byte stream;
4. `ONE_OF_OPTION` = text/flags/value and `DEFAULT` = id/type/value (length = 5 + width,
   observed 231×6, 59×7, 6×9 for widths 1/2/4);
5. `REF` = …/flags/target-form(+GUID), 15 vs 33 bytes, and self-referencing `REF` = button;
6. string package header (type 0x04, header size 0x34, first block at `+0x34`) and the SIBT
   walk producing sane text (`id 6 = "Setup"`, `id 8 = "Main"` are the two form titles used by
   the root form's opcodes);
7. every item offset fits its varstore; 323/323 `one_of` defaults are among their own option
   values; 173/175 numeric defaults inside `[min,max]` (the 2 exceptions are the signed ones).

Inferred / not proven (do not rely on it as byte truth):

* **Condition → item binding.** Each condition wrapper is closed by its own `END` *before* the
  item that it governs (`SUPPRESS_IF expr END item END`), while items are also closed by `END`;
  the parser therefore keeps a wrapper pending until the next item and pops one consumed wrapper
  per later `END`.  This reproduces the mutually exclusive TPM variants
  (`qid 0x01B0/0x01AF/0x01B1` on forms `0x271e/0x271f/0x2720`) and yields
  `rules` for 284 items, but the exact nesting of *nested* wrappers
  (`gray-out{ suppress{ … } }`) is a heuristic; `meta.notes.ignored_end = 1206` counts the
  item-`END`s.  Treat `rules` as advisory.
* `GUID_OP` with AMI GUID `0F0B1735-87A0-4193-B266-538C38AF48CE` + u16 token (22×, H/W Monitor
  page): layout read, meaning (sensor/fan callback) unknown.
* `SETUPLAYOUTINFO`, `ASRPlatformData`, `ASRockEasySetup`-driven page re-ordering: not decoded.
* The 26 varstores without questions, the 12-byte table prefix at `0x690479`, the auxiliary
  tables in `0x690000..0x690488`, and the meaning of the descriptor `flags`/`guid` fields of the
  tag `0x26` record.
* Dynamic option lists: 5 items (e.g. `System Language`, XMP profiles) have options whose texts
  are empty strings in the pool (ids point at empty entries) — the setup fills them at runtime,
  so value → label for those is not recoverable from the ROM (`meta.counts.items_with_dynamic_options`).
* ASRock string placeholders such as `DDR5-%d %d-%d-%d-%d %d.%dV` are kept as-is.

## 8. Validation against the ROM factory defaults

Method: `tools/uefi/nvarstore.py:load_defaults()` (AMI NVAR factory-default store, ROM region
`0x1bc0000`) gives 17 default varstores including `Setup` (604 B).  For each decoded item the
bytes `blob[offset : offset+size]` are read little-endian and matched against the item's option
list; separately the IFR `DEFAULT`/option-flag default is compared with the ROM value.

Aggregate: `516/635` items have a decodable ROM default; `502` of them also carry an IFR default
and **501 agree byte-for-byte** (the single difference is `System Language`, whose varstore holds
the 2-byte code `0x6e65` "en" while the IFR default is the list index 0 — a runtime-translated
question, not a decode error).

10 rows (offset inside the varstore → name → value from the ROM defaults):

| varstore | off | size | type | qid | ROM value | option text | name | IFR default |
|---|---|---|---|---|---|---|---|---|
| `AMITSESetup` | 0x050 | 1 | checkbox | 0x0136 | 0x01 (1) | Enabled | Full Screen Logo | 1 |
| `ASRockEasySetup` | 0x000 | 1 | one_of | 0x005C | 0x00 (0) | Advanced Mode | UEFI Setup Style | 0 |
| `NetworkStackVar` | 0x000 | 1 | one_of | 0x00D2 | 0x01 (1) | Enabled | Network Stack | 1 |
| `PCI_COMMON` | 0x003 | 1 | checkbox | 0x7006 | 0x01 (1) | Enabled | Above 4G Decoding | 1 |

## 9. Output shape

`out/settings_map.json` (combined nine-formset output):

```
meta            source, first-formset ifr/string_package for compatibility,
                formsets[9]{formset,ifr,string_package,languages,varstore_table,notes,...}
varstores[78]   name, size, guid, guid_name, id, questions, max_offset_used, db_offset, formset
forms[544]      id, title, path, questions, submenus, buttons, reachable, ifr_offset, formset
gotos[645]      kind(goto|action), form, label, target_form, target_guid, qid, cross_formset, formset
items[4943]     path, menu, name, form, varstore, varstore_id, offset, size, type, qid, help,
                options[{value,text,flags,is_default}], min/max/step, signed, flags,
                defaults[{id,value}], default, default_source, rules{suppress_if|gray_out_if|disable_if},
                ifr_offset, rom_default, formset
counts          aggregate counts for all nine formsets
```

For a dump editor the actionable triple is `items[].varstore + offset + size` → value, with
`options[]` for `one_of` / `checkbox` and `min/max/step` (+`signed`) for `numeric`;
`rom_default` is the factory value, `default` the IFR factory value (they agree on 501/502).
